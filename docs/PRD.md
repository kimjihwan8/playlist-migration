# PRD — 플레이리스트 이전 서비스 (가칭: Playlist Migrator)

> Product Requirements Document · v0.1 · 2026-07
> 작성 목적: 프론트엔드 취업 포트폴리오 (+ 백엔드/서버리스 역량 어필)

---

## 1. 개요 (Overview)

음악 스트리밍 플랫폼 간에 플레이리스트를 옮기는 웹 서비스. 소스(예: 다른 플랫폼에서 뽑은 CSV, Spotify)의 곡들을 타겟 플랫폼(Spotify 우선)에서 **다시 찾아(매칭)** 재구성한다.

핵심 난제는 "복사"가 아니라 **"매칭"** 이다 — 플랫폼마다 같은 곡의 ID가 다르기 때문에, 곡을 타겟에서 검색·식별해 다시 담아야 한다. 이 매칭 엔진의 정확도가 제품 품질의 핵심.

## 2. 문제 정의 (Problem)

- 사용자가 스트리밍 서비스를 갈아탈 때, 수백 곡의 플레이리스트를 수동으로 옮기는 것은 비현실적.
- 기존 상용 도구(TuneMyMusic, Soundiiz 등)가 있으나, 본 프로젝트의 목적은 **매칭 엔진을 직접 설계·구현**해 엔지니어링 역량을 증명하는 것.

## 3. 목표 & 핵심 서사 (Goal & Narrative)

- **제품 목표:** 플레이리스트를 높은 정확도로 타겟 플랫폼에 이전한다.
- **포트폴리오 서사(핵심):** "처음엔 ISRC만으로 매칭 → 매칭률이 낮은 이슈 발견 → 제목+아티스트+재생시간 **계단식(cascading) 폴백**으로 매칭률 개선." `ISRC-only 매칭률` vs `계단식 매칭률` 두 숫자를 **실측**해 정량 개선치(예: 68% → 94%)를 제시한다.
- **원칙:** 모든 기술 선택은 "문제 → 선택 → 트레이드오프"로 정당화한다. (resume-driven development 금지)

## 4. 타겟 사용자 (Users)

- 스트리밍 서비스를 이전/병행하려는 개인 사용자.
- (포트폴리오 맥락) 데모·평가자. 대중 공개는 비목표 — 개발/테스트 모드로 운영.

## 5. 범위: 단계별 로드맵 (Scope / Phasing)

각 Phase는 **독립적으로 동작·데모 가능**하도록 쪼갠다.

> **범위 재조정(2026-09): OAuth-first.** CSV-only 첫 MVP를 버리고, 처음부터 OAuth 계정→계정 이전으로 시작. CSV는 보조 소스(P4+)로 강등.

| Phase | 내용 | 인증/인프라 | 서사 역할 |
|-------|------|------------|----------|
| **P1 (첫 MVP)** | Spotify **OAuth(PKCE)** 로그인 → 소스 플리 읽기 → **ISRC 매칭** → 타겟 계정에 **쓰기**. **동기 처리**(작은 플리, 29초 내). 토큰은 httpOnly 쿠키/서버세션 | OAuth. **Next.js API routes on Vercel**. 전용 DB·큐 ❌ | **진짜 이전** 성립 + **ISRC-only 베이스라인 매칭률** 측정 |
| **P2** | 큰 플리 타임아웃(29초/Lambda 15분) · 크래시 자동복구 부재 · 공유 레이트리밋 429 문제에 부딪혀 → **async 워커 + DynamoDB + 진행률 폴링 → 이어서 SQS 도입**(자동 재배달·중앙 동시성 제어) + 워커 1→2 병렬 | **AWS** Lambda+DynamoDB(+SQS) | **"동기→비동기 진화"** climax (측정→진화 서사) |
| **P3** | **fuzzy 계단식 매칭** + 애매매칭 **리뷰 UI** | — | 매칭률 개선 서사의 climax |
| **P4+** | 크로스플랫폼 어댑터(YouTube/Apple $99), **CSV 소스(보조)**, auto-sync | 어댑터 추가 | 확장성 증명 |

> **아키텍처 = 하이브리드.** 디자인이 Next.js로 나옴 → 프론트+P1 백엔드(OAuth콜백·검색·쓰기)=**Next.js API routes on Vercel**. P2 비동기 파이프라인(워커·큐·DB)만 **AWS**. "각 작업에 맞는 도구"가 올-AWS보다 정직·설득력↑.
> **⚠️ OAuth-first 결과:** ①1번 화면이 CSV 드롭존 → "Spotify 로그인→소스 플리 선택"으로 변경(CSV는 보조 탭 유지). ②Spotify 개발자 앱 셋업 P1부터 필요(client_id/secret, redirect URI, 개발모드 화이트리스트 최대5명, 스코프 playlist-read-private·playlist-modify-*).

## 6. P1 상세 기능 (First MVP)

### 6.1 사용자 흐름 (OAuth-first)
1. 사용자가 Spotify **OAuth(PKCE) 로그인** (스코프: playlist-read-private, playlist-modify-public/private)
2. 소스 플레이리스트 선택 → 곡 목록 읽기 → 공통 Track으로 정규화
3. ISRC 있는 곡마다 Spotify에 ISRC 검색 (매칭)
4. 타겟 플레이리스트 생성 + 매칭된 곡 **쓰기**(추가, 100곡/요청 배치)
5. 결과표: 각 곡 → 매칭·이전됨 또는 실패(사유)
6. 요약 통계: "N곡 중 매칭 X, 실패 Y (ISRC없음 a · 타겟에없음 b)" + **ISRC-only 베이스라인 매칭률**
- ※ 동기 처리: 작은 플리(29초 내)만. 큰 플리는 P2에서 비동기로.

### 6.2 P1에서 되는 것 / 안 되는 것
- ✅ OAuth 로그인, 소스 플리 읽기, ISRC 매칭, **타겟 계정에 실제 쓰기**, 매칭/실패 분류·사유, 매칭률 통계·결과 뷰
- ❌ 큰 플리 비동기 처리·진행바·크래시 복구(P2), fuzzy(P3), 크로스플랫폼·CSV 소스(P4+)

## 7. 성공 기준 (Success Metrics)

- **P1:** 테스트셋(예: TuneMyMusic로 이전한 결과를 정답지로) 기준 **ISRC-only 매칭률을 측정·기록**. 결과 CSV가 정상 생성. 실패 사유가 정확히 분류됨.
- **P3:** fuzzy 도입 후 매칭률이 베이스라인 대비 유의미하게 상승(정량 개선치 확보).
- (포폴) 각 기술 선택의 "문제→선택→트레이드오프"를 README·블로그로 설명 가능.

## 8. 비목표 (Non-Goals)

- 회원가입/영구 계정 시스템 (100% 무회원, Job 중심).
- 사용자 음악 데이터의 영구 저장·재판매 (정책 위반 회피, TTL 자동삭제).
- 대중 공개 서비스 운영/스케일 (개발·테스트 모드로 충분).
- 멜론·지니 등 공개 API 없는 국내 플랫폼 (범위 제외).

## 9. 제약 & 리스크 (Constraints & Risks)

- **Spotify 개발자 정책(2026.2):** 개발 모드 앱은 화이트리스트 최대 5명. 대중 공개엔 심사 필요 → 포폴엔 무관.
- **플랫폼별 API 상이:** 각 플랫폼은 어댑터로 격리 (확장성).
- **YouTube:** 공식 API는 "영상 재생목록"만(YouTube≠YouTube Music), Premium은 API와 무관. → P4 이후.
- **Apple Music:** 구독≠개발권한. 라이브 어댑터엔 $99/년 필요 → 테스트 데이터로만 쓰면 불필요.
